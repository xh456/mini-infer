# W1 学习笔记：推理的两段式与 KV Cache

> 这份笔记是 W3 手写 forward 的前置知识。公式推不出来，代码一定写不对。

## 1. 为什么要把 prefill 和 decode 分开看

LLM 推理在物理上是两个性质完全不同的阶段：

| | prefill（处理输入） | decode（逐 token 生成） |
|---|---|---|
| 并行度 | 全部输入 token 同时算 | 一次只有 1 个（或 batch 个）token |
| 瓶颈 | 计算（compute-bound） | 显存带宽（memory-bound） |
| 优化手段 | FlashAttention、大 tile、算子融合 | 批处理、量化、投机解码、PagedAttention |

**算术强度**（每访问 1 字节显存能做多少次浮点运算）是判断瓶颈的唯一标准。

以 fp16 为例：每个参数占 2 字节，每个 token 的前向需要约 2 次浮点运算，
所以 **decode 时算术强度 ≈ 1 FLOP/Byte**。

而消费级 GPU 的平衡点约等于「算力 ÷ 带宽」。RTX 4090 大致是
330 TFLOPS(fp16) / 1.0 TB/s ≈ **330 FLOP/Byte**。

结论：batch=1 的 decode，算术强度 1，平衡点 330，**GPU 会被显存带宽饿死，
算力利用率不到 1%**。这就是为什么提高吞吐几乎等价于"想办法把 batch 做大"。

反过来，一次 2048 token 的 prefill：FLOPs = 2 × 参数 × token ≈ 2.0 TFLOPs，
需要搬运的权重只有约 1 GB，算术强度 ≈ 2000 FLOP/Byte，**远高于平衡点，
因此是计算受限**——这也是 FlashAttention 这类减少显存往返的技术能生效的地方。

## 2. KV Cache 显存公式

自回归生成时，已生成的 K/V 不必重算，缓存起来：

```
KV bytes = 2 (K与V) × 层数 × KV头数 × head_dim × dtype字节 × 序列长度 × batch
```

以 **Qwen2.5-0.5B-Instruct**（hidden=896，24 层，14 个注意力头，
2 个 KV 头，head_dim=64，fp16 = 2 字节）为例：

```
每 token = 2 × 24 × 2 × 64 × 2 = 12,288 字节 ≈ 12 KiB
4096 token 的单条序列 = 12 KiB × 4096 ≈ 48 MiB
32 条并发 × 4096 token ≈ 1.5 GiB
```

对照：如果这 2 个 KV 头换成标准多头注意力（14 个 KV 头），

```
每 token = 2 × 24 × 14 × 64 × 2 = 84 KiB   →   7 倍
```

**这就是 GQA（分组查询注意力）的全部意义**：它让显存占用降到 1/(14/2)，而精度损失很小。
面试被问到"为什么现在的模型都用 GQA"，答案就是这个除法。

权重本身的体量可以顺手算出来：0.494B 参数 × 2 字节 ≈ 0.99 GB（fp16）。
所以 0.5B 模型在 24 GB 卡上，显存几乎全部被 KV Cache 和激活吃掉——
推理引擎的显存管理，管的就是这一块。

## 3. 连续批处理（Continuous Batching）为什么有效

**静态批处理的问题**：一批请求必须等最慢的那条生成完才能整体返回，短请求白占算力。

**连续批处理的做法**：以 token 为粒度调度——每个 decode step 结束后，
立即把已完成的序列踢出、把排队中的新序列加入，让每个 step 的 batch 始终装满。

为什么这能提升吞吐（而不是只是"公平"）：

1. 权重在每个 decode step 只需要**读一次**，现在这一次读取服务了 B 个 token，
   算术强度从 1 提升到约 B，把内存密集的 decode 逐步推向计算密集；
2. 于是吞吐从"带宽决定的约 1000 tok/s 上限"变成"算力决定的上限 × 利用率"，
   在 4090 上量级可以差几十倍；
3. 但提升不是无限的：一旦算术强度接近 330 这个平衡点，再加大 batch 就没有收益了，
   反而会增加显存压力和单请求延迟。**存在最优 batch，需要实测找出来**——
   这正是 W9 里"批大小-吞吐曲线"要画的东西。
