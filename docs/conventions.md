# 开发约定

> 这些约定不是形式主义。面试官会打开你的 GitHub，提交记录的质量直接等于他判断你工程素养的依据。

## 分支模型

| 分支 | 用途 | 规则 |
|---|---|---|
| `main` | 始终保持可运行 | 只接受合并，不直接在上面开发 |
| `feat/<主题>` | 单个功能 | 例：`feat/rope-attention` |
| `exp/<主题>` | 一次性实验 | 例：`exp/int8-calibration`，结论写进 docs/ 后可删 |
| `fix/<主题>` | 修 bug | 例：`fix/kv-cache-offset` |

流程：本地开分支 → 小步提交 → 合并回 `main`（哪怕只有你自己，也走这个流程，
因为合并记录本身就是"这个人有工程习惯"的证据）。

## 提交信息

格式：`<type>(<scope>): <中文或英文描述>`

| type | 含义 |
|---|---|
| `feat` | 新功能 |
| `fix` | 修 bug |
| `perf` | 性能优化（**必须带数字**，例：`perf(attention): decode 吞吐 412 → 688 tok/s`） |
| `refactor` | 重构，行为不变 |
| `test` | 测试 |
| `docs` | 文档 |
| `chore` | 环境、依赖、脚手架 |
| `bench` | 基准测量与结果 |

规则：

1. 一次提交只做一件事。写不出干净的提交信息，说明这个改动应该拆开。
2. 提交信息里不要出现"修改"、"更新"、"优化一下"这类无信息量的词。
3. 性能相关的提交必须带数字和硬件，否则半年后无法追溯。
4. 不提交注释掉的废弃代码——`git log` 就是你的回收站。

## 实验记录

任何"这个改动有没有用"的问题，都必须按 [`experiment-template.md`](experiment-template.md) 记录：

- 四要素（硬件 / 软件版本 / 实验配置 / 指标）缺一不可；
- 结果落成 `bench/results/*.json` 而不是截图或聊天记录；
- 失败的实验也要记——面试时"我试过什么、为什么不行"往往比成功更值钱。

## 复现性红线

1. 依赖版本全部固定，不写 `torch>=2.0`。
2. 随机种子固定（`torch.manual_seed`），测量类脚本必须关闭随机采样。
3. 所有测量脚本必须支持"换一台新机器，一条命令跑出同一组数字"。
4. 图片与曲线全部由脚本生成，不手工画图。

## 代码风格

- Python：4 空格缩进，类型注解，函数与类写 docstring（说明"为什么"而不是"做了什么"）。
- C++/CUDA：`csrc/` 下按模块分目录，每个 kernel 都要有对应的正确性测试。
- 注释写取舍理由：`// 这里用单缓冲而非双缓冲，因为显存紧张时双缓冲的收益被带宽吃掉`
